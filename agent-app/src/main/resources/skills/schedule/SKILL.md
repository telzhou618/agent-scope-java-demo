处理定时任务时，**必须调用定时任务工具落地**，不允许只在回复里声称已经创建、修改或删除。可用工具：

- `list_schedules`：查询当前用户的定时任务（id、标题、cron、状态、上次/下次执行时间）
- `create_schedule(title, description, cron)`：创建
- `update_schedule(id, title?, description?, cron?)`：修改，只传需要改的字段
- `delete_schedule(id)`：删除
- `trigger_schedule(id)`：立即执行一次，不等下个周期

## 创建流程

1. 先 `list_schedules` 查一遍：已有同名或同周期的任务，改用 `update_schedule`，不要重复创建。
2. `title` 写简短可读的标题，例如「每周运营报告」。
3. `cron` 是 **Quartz 6 段**表达式（秒 分 时 日 月 周），不是 Linux crontab 的 5 段：
   - 每天 8 点：`0 0 8 * * ?`
   - 每周一 9 点：`0 0 9 ? * MON`
   - 每月 1 号 0 点：`0 0 0 1 * ?`
   - 「日」和「周」不能同时给具体值，另一个写 `?`
4. `description` 只写到点后**要做的那件事**，用 Markdown 写清目标、步骤、产出、输出格式；不要出现任何执行频次、执行时间、周期、定时、cron 字眼（如「每天」「每周一」「定期」「几点」）。周期完全由 cron 表达——到点执行时任务里看不到 cron，只看得到这段描述。
5. 创建成功后把 `nextRunAt` 告诉用户。

## 执行与确认

- `trigger_schedule`、`delete_schedule` 属于确认类工具：调用会被挂起，前端弹确认卡，用户确认后才真正执行。调用前先跟用户说明将要做什么。
- 工具返回 `{"success": false, "error": "..."}` 时，把 error 原文转述给用户；不要反复重试同一个调用。

## 禁止事项

- **禁止在定时任务执行过程中创建或修改定时任务**：如果你这一轮是被某个定时任务触发的（任务正文只有「要做的事」、没有周期），只完成那件事本身，不要再建任务——工具侧会直接拒绝这类调用。
- 不要把周期塞进 `description` 来绕开限制。
